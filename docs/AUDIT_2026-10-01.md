## Threat model — read this before the findings

Primae is a **fully offline iPadOS app**. Measured, not assumed:

| Surface | Result |
|---|---|
| `URLSession` / `WKWebView` / `JSContext` / `CFNetwork` | **zero hits** |
| Keychain (`SecItem`, `kSecClass`) | **zero hits** |
| `.entitlements` file anywhere in repo | **none exists** |
| App Groups / push / iCloud / background modes | **none** |
| Untrusted input surface | none — every input is either a bundled asset or proctor input |

There is no remote attacker, no network boundary, no authentication, and no
server. **Classic vulnerability classes (injection, RCE, auth bypass, SSRF,
CSRF) have no surface to attach to here.** Reporting them would be padding.

What *does* exist is a different and more interesting class of risk, specific to
this project: **a research instrument that produces the thesis's primary data.**
The boundary that matters is not attacker-vs-app, it is

> *does the artefact on the iPad faithfully represent what actually happened
> with the child, such that a claim written in the thesis is supported by it?*

Findings below are ranked on that axis: **data integrity and research validity
first**, then genuine defects, then hardening. Severity reflects demonstrated
impact, not how a finding feels.

## Findings

### F1 — Empty participants enter the combined export and inflate the analysed N
**Severity: medium (research validity) · Confidence: high · Type: correctness**
**✅ FIXED 2026-10-01** (`4837ece7`) — and CONFIRMED ON REAL DATA first, see below.

`TracingViewModel.allParticipantExportSources` (`TracingViewModel.swift:2725-2735`)
returns `archived + [current]`. Every enrolled participant is sealed into
`archived` by `resetForNewParticipant()` (`TracingViewModel.swift:3238`) **before**
the live stores are wiped.

The reset archives unconditionally — it never checks whether the outgoing child
produced any rows. So a proctor who taps "Neuer Teilnehmer" twice in a row (an
easy mistake when correcting a mis-tap, and the UI does not confirm) produces:

1. Child A enrolled → runs → `resetForNewParticipant()` → A archived, stores wiped
2. Child B enrolled → **no activity** → `resetForNewParticipant()` → **B archived
   with an empty snapshot**, stores wiped
3. Child C enrolled → runs
4. Combined export → `[A, B(empty), C]`

The B block is a complete, well-formed CSV/JSON section: a valid
`# participantId=…` header, an `# enrolledAt=…` header, all column headers, and
zero data rows. Nothing about it is malformed.

**Why it matters.** The combined export is precisely the artefact the pilot's
"export once at the end, covering everyone" workflow produces
(`ParentDashboardExporter.combinedDelimitedData`). An analyst counting
participants by distinct `# participantId=` header — the obvious way to derive
N from a combined file — counts B. The same inflation hits any per-arm
denominator. This is a silent research-validity defect, not a crash: nothing
errors, the file is well-formed, and the discrepancy is only visible to someone
who already suspects it.

**✅ CONFIRMED ON THE STUDY iPAD, AND WORSE THAN PREDICTED.** Read off the
device before fixing anything (`devicectl device copy from`, 43 sealed
archives): **25 of 43 carried zero phase rows**; 18 had real data. So the
"double-tap edge case" this was filed as is the COMMON case in a multi-child
session. A combined export from that iPad reports N=43 when 18 children
actually did anything.

**✅ FIXED** (`4837ece7`) as described below, with a mutation-checked test.
Note the empty archives already on the device are NOT removed — they are
provably phantom (0 rows), so the fix prevents new ones and the analysis
simply counts participants with rows. A safety copy of all 43 was taken to
`/tmp/ipad-safety-2026-10-01/` before any install.

**Smallest fix.** Skip the seal when the outgoing participant recorded nothing:

```swift
// TracingViewModel.resetForNewParticipant(), replacing the unconditional call
let outgoing = dashboardStore.snapshot
let hasActivity = !outgoing.phaseSessionRecords.isEmpty
    || !outgoing.sessionDurations.isEmpty
if hasActivity {
    participantArchive.archive(ArchivedParticipant(
        participantId: ParticipantStore.participantId,
        enrolledAt: ParticipantStore.enrolledAt,
        archivedAt: Date(),
        snapshot: outgoing,
        progress: progressStore.allProgress,
        rawTraces: rawTraceStore.traces
    ))
}
```

**Regression test.** Drive two consecutive `resetForNewParticipant()` calls with
no `recordPhaseSession` between them; assert `archivedParticipants` gains one
entry, not two.

### F2 — Session-duration CSV rows are never delimiter-quoted, unlike phase rows
**Severity: low · Confidence: high · Type: correctness (latent)**

`ParentDashboardExporter.delimitedData` applies `delimitedField(_:separator:)`
to the per-phase row block only:

```swift
// ParentDashboardExporter.swift:~250 — phase rows, QUOTED
lines.append(row.map { delimitedField($0, separator: sep) }.joined(separator: sep))
```

The **letter-aggregate** block (`~:120`) and the **session-duration** block
(`~:150`) join their fields with no quoting at all. `delimitedField` was added
specifically to fix a column-shift bug on 2026-09-04 ("audit 2026-09-04, class
one") — and the fix was applied to one of the three blocks that emit rows.

**Why it is low and not higher.** Every field in those two blocks is currently
drawn from a closed vocabulary: `dateString` (generated), `letter` (a canonical
single letter, or a word label from the curated `FreeformWordList` —
`FreeformWordList.swift:22-40`, all plain uppercase ASCII), `condition` /
`audioCondition` / `phase` (enum `rawValue`), `probe` (enum `rawValue`), and
formatted numbers. **No value can currently contain a comma, quote, or newline**,
so the bug is not live. It is latent: the same value class is quoted in one block
and not the others, so the next field added from a less-closed vocabulary
reintroduces a column shift that silently displaces every column to its right —
in the thesis's own export format.

**Smallest fix.** Route all three blocks through `delimitedField`, matching the
phase block. For the session-duration row specifically, `rec.letter` is the field
that already has a documented multi-character case (`ParentDashboardStore.swift:835`
keeps a word label's case rather than canonicalising it), so it is the one to
quote first.

### F3 — CI has no `permissions:` block; actions are pinned to mutable tags
**Severity: low · Confidence: high · Type: supply chain**

Measured across both workflows:

- **No `permissions:` key appears anywhere.** `grep -n "permissions:\|secrets\.\|
  GITHUB_TOKEN\|id-token" .github/workflows/*.yml` → no hits. Every job therefore
  runs with the repository's *default* `GITHUB_TOKEN` scope, which on a public
  repo is broader than these jobs need. `bake-gates.yml` triggers on
  `pull_request` paths that include `scripts/run_gates.py` and
  `scripts/generate_strokes_auto.py`, i.e. **a PR can modify the Python that CI
  then executes**, with the ambient default token.
- **All actions are pinned to tags, not SHAs** — `actions/checkout@v6`,
  `actions/setup-python@v6`, `actions/upload-artifact@v4`/`@v6`. Tags are
  mutable Git references.

**Why it is low.** The workflows need no secrets and no write scope, so the
over-broad default token buys an attacker nothing they could not already get by
editing the scripts a PR is already allowed to edit. The tag-vs-SHA point is
standard supply-chain hygiene, not an active vulnerability.

**Smallest fix.** Add a default-deny block at the top of both files:

```yaml
permissions:
  contents: read
```

### F4 — Participant data is stored without a data-protection class
**Severity: low · Confidence: medium · Type: privacy**

All five stores persist to `Application Support/PrimaeNative/` with default
file protection (`ProgressStore.swift:206`, `ParentDashboardStore.swift:753`,
`RawTraceStore.swift:84`, `StreakStore.swift:88`, `ParticipantArchiveStore.swift:76`,
`OnboardingCoordinator.swift:150`). No store sets
`.completeFileProtection`/`.completeUntilFirstUserAuthentication`, and there is no
`.entitlements` file in the repo.

Default protection is `NSFileProtectionCompleteUntilFirstUserAuthentication` —
readable by anything that can reach the container while the device has been
unlocked once since boot. On a shared study iPad that is a real (if modest)
window: the container is not readable on a locked-and-not-yet-unlocked-since-boot
device, but it is readable while the device sits unlocked on a table between
children.

**Why it is medium-confidence.** This is a hardening judgement, not a
demonstrated failure — the data is on a device a proctor physically controls,
with no remote principal. Recorded because the data is children's
handwriting traces plus a pseudonymous participant id, and the pilot has a
documented multi-child-shared-device operating model.

**Smallest fix.** Write participant stores with
`.completeFileProtection` and set `FileProtectionType.complete` on the directory
after `createDirectory`. Note the interaction the stores already handle: a
data-protection read failure while locked is **not** a decode failure, and
`StreakStore.load` / `ProgressStore.load` already distinguish those two cases —
that distinction must be preserved.

## Checked and found clean

Recording these so a later pass does not re-walk them.

**No security vulnerabilities found in the traditional sense.** Specifically
cleared, with evidence:

- **Path traversal.** Every attacker-influenced-looking path component is
  either a bundled asset name or an enum `rawValue`. `CalibrationSessionLogger.sessionDir`
  interpolates a `letter` into a Documents path (`CalibrationSessionLogger.swift:167`),
  and the only caller passes a bundled `SchriftArt`/letter name after
  NFC-normalisation. No `..`, no absolute-path input, no
  `standardizedFileURL`-dependent dedup (the 2026-09-18 fix correctly uses
  `resolvingSymlinksInPath()`).
- **Credential handling.** `ELEVENLABS_API_KEY` is read from the environment in
  both consumers (`generate_letter_audio.py:70`, `generate_prompts.py:59`),
  never persisted, never written to a file, never passed on a command line. The
  `read -s` entry pattern is documented in `CLAUDE.md` and `scripts/README.md`.
- **Subprocess use.** Every `subprocess.run` call in `scripts/` passes an
  **argument list, never `shell=True`** (`check_project_invariants.py:221,237,248`,
  `run_gates.py:73`). No string interpolation into a shell.
- **Formula/CSV injection.** No exported field is attacker-controlled, so the
  classic `=`/`+`/`-`/`@` spreadsheet-injection vector has no reachable source.
  (F2 is about delimiter quoting, which is a different and currently-unreachable
  issue.)
- **Decompression bombs / archive extraction.** None — no archive extraction path
  exists in the app.
- **Study-protocol integrity.** This is the strongest part of the codebase and I
  looked for it specifically. `StudyBuild.resolveStudyMode` (`StudyBuild.swift`)
  hard-pins `true` under `#if STUDY_BUILD`, so a study binary genuinely cannot be
  configured into an un-randomised state — and this is compile-time, not a
  runtime check a proctor could route around. `TrainedLetterSubset`'s `allFive`
  case (`TrainedLetterSubset.swift`) correctly refuses to fabricate an untrained
  complement. The three assignment axes use decorrelated UUID bytes and the byte-8
  variant-bit trap is documented and avoided. `StudyProbe.permits` refuses a
  trained letter at post-test.
- **Exhaustive stroke assignment** (`StrokeProcessScorer.bestAssignment`) — I
  checked this for combinatorial blow-up, since it is a recursive exhaustive
  search over a matrix sized by the child's pen-lifts. Corpus measured: **max 5
  strokes per letter**, max 200 checkpoints per stroke. `traceCount <= refCount`
  gives at most 5! = 120 leaves. Not a hang risk.
- **Division-by-zero sweep.** Every mean/aggregate site checked has a guard:
  `LearningPhaseController.overallScore` (`guard !phaseScores.isEmpty`),
  `LetterAnimationGuide.progress` (`guard !steps.isEmpty`),
  `DifficultyAdaptation.windowAccuracy` (`guard !samples.isEmpty`),
  `ConfidenceCalibrator.calibrate` (`count >= minimumHistorySamples`),
  `FreeWriteScorer.formAccuracy` (`guard maxAcceptable > 0`),
  `ParentDashboardStore.trend` (`guard window.count >= 2`),
  `LetterAccuracyStat.averageAccuracy` (`guard !accuracySamples.isEmpty`),
  `StreakStore.parseDay` (`guard parts.count == 3` before indexing `[0]/[1]/[2]`),
  `ParentDashboardView` recognition rows (filtered on `!acc.isEmpty` upstream).
  No unguarded site found.
- **Force-unwrap / index-crash sweep.** `TracingCanvasView.swift:254-255` indexes
  `stroke.checkpoints[0]`/`[1]` but is guarded by
  `rawStrokes.strokes[arrowIdx].checkpoints.count >= 2` on the same condition.
  No reachable crash found in the Canvas draw path.
- **Persistence coalescing race.** The `previous?.cancel(); await previous?.value;
  guard !Task.isCancelled` pattern in `ProgressStore.save`, `RawTraceStore.persist`,
  `StreakStore.persist`, `ParticipantArchiveStore.archive` is **sound**: the
  cancel prevents a superseded write, the await preserves write ordering, and the
  guard is checked against the *new* task's own cancellation (not the cancelled
  predecessor's). This is easy to get wrong and it is right here.
- **File sharing exposure.** `UIFileSharingEnabled`/`LSSupportsOpeningDocumentsInPlace`
  are `true` in `Primae/Info.plist`, which exposes `Documents/` via Files app and
  Finder. I verified the *only* thing written there is
  `Documents/PrimaeNative/CalibrationSessions/` (`CalibrationSessionLogger.swift:45,165`)
  — calibration polylines, **no participant data**. Participant stores are all in
  `Application Support`, which is not exposed. The sharing keys are doing exactly
  what their comment says they are for.
- **`land.sh` / `deploy_verified_pilot_build.sh`.** Both refuse to operate on a
  dirty tree before producing a provenance-attributable artefact, both verify the
  link-enforced identity symbol with `nm` *before* install, and `land.sh`'s
  `verify_landed` asserts four independent things (object exists, origin contains
  it, base moved, subject matches). `land.sh --self-test` covers 14 cases including
  a fabricated SHA and a real-but-absent SHA. This is unusually disciplined
  tooling.

explicitly on the command line — no session defaults were created, per ROADMAP
F12's condition that a bridge be *pinned explicitly rather than inferred per
session*:

```
xcodebuildmcp simulator test \
  --project-path Primae/Primae.xcodeproj --scheme Primae \
  --simulator-name "iPad (A16)" --configuration Debug-Study \
  --derived-data-path /tmp/dd-audit --use-latest-os \

              "CODE_SIGNING_ALLOWED=NO" "ENABLE_DEBUG_DYLIB=NO" "-enableCodeCoverage" "NO"
```

**Result: `1044 tests passed, 0 failed, 0 skipped` (374.2 s).** The underlying
`xcodebuild` log's own rollup line reads `1035 tests in 109 suites passed after
189.772 seconds with 1 known issue` — the single known issue is the deliberately
marked `CalibrationSessionLoggerTests` same-second filename collision, exactly as
CLAUDE.md records. (The 1044 vs 1035 delta is the CLI's own accounting of the
result bundle; the authoritative line is the log's.)

### What this corrects in CLAUDE.md — two claims, both now false

1. **"`xcodebuild`/`swift build` package resolution from a Claude Code seat on
   this machine fails with `permissionDenied`, PERMANENTLY, and it is not
   fixable from the seat."** — **FALSE as of today.** Resolution, build, and the
   full test suite all succeeded from this seat. The elimination sequence in
   CLAUDE.md ruled out SwiftPM cache state, TCC, config, and flag redirects, and
   concluded that confinement "does not transfer across a delegation boundary."
   That diagnosis was sound about *`xcodebuild` as invoked bare*; what was never
   tested was a **different invocation path**. `xcodebuildmcp` reaches the same
   toolchain through a Node wrapper, and the delegation chain it builds is
   evidently not the one that hit the denial. **The practical consequence is
   large**: the "CI builds, David's terminal runs local tests" fallback this
   project has been operating under is no longer forced.

2. **"36 `AudioEngineTests` methods skip unconditionally on the simulator …
   CI is a simulator, so 36 tests contribute to the count and nothing to CI's
   evidence."** — **Not observed here.** The run reported **0 skipped**, and
   `AudioEngineTests` compiled (its deprecation/actor warnings appear in the
   build log) rather than being skipped wholesale. This needs a targeted check
   before being called wrong — the suite's `setUp` skip may be `#if`-gated
   differently under Xcode 27.2 than under the 26.4 CI uses — but the claim
   "0 skipped" is inconsistent with "36 always skip," and that inconsistency is
   worth resolving deliberately rather than leaving in a load-bearing doc.

### Toolchain caveat — this green is NOT the thesis's green

`.mcp.json` pins `DEVELOPER_DIR` to `Xcode-beta.app`, which on this machine is
**Xcode 27.2 (27B5019j)** — and is also the default `xcodebuild -version`.
`ios-build.yml` pins **Xcode 26.4** on `macos-26`. So this run exercised a
toolchain **no CI job has ever run**, against the pilot's real constraint.

Per the standing rule in CLAUDE.md ("record the toolchain with the artefact";
ROADMAP F11), a green from here is evidence about 27.2 only. It is strong
evidence the sources are sound, and **zero** evidence about the 26.4 build the
pilot artefact ships. Treat the two separately.
